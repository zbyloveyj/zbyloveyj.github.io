## 01 · 理解概念

### 批准的是具体动作与具体内容

“可以写报告”仍不够具体。一次可检查的批准应当说明写在哪里、准备写什么，以及执行会改变什么。本课固定写入项目输出目录中的 approved_report.txt，避免把演示扩展成任意路径写入工具。

第一次运行时不要填批准值。先阅读 preview 和 digest；程序应停在 needs_approval。只有你看过将写入的内容，才把相应摘要复制到 approved_digest 中，再运行同一任务。

### 摘要把批准和内容联系起来

本课摘要由固定目标路径与待写内容共同计算。相同目标和内容得到相同摘要；内容改变后，之前的批准不应继续适用。这能减少“审阅的是旧稿，执行的是新稿”的错误。

摘要不是加密，也不是完整的权限系统。本课的摘要用于把一次演示批准与文件内容联系起来。真实产品还需要验证批准者身份、权限、有效期与操作目标。

### 幂等让重复请求不重复做事

网络中断后用户可能再点一次提交。幂等设计让同一批准、同一内容重复提交时，报告 already_applied，而不是重复追加或制造多个副本。这里判断的是相同操作是否已经执行。

幂等不等于所有状态永远不变。新内容应产生新的摘要与新的审阅要求；不同动作还需要不同的操作标识。把全局“已批准”布尔值当作永久授权，会失去这层边界。

### 在科研流程中使用审阅节点

你可以把写入前预览迁移到分析报告、候选文献清单或批量文件整理。自动化负责准备结果，人负责确认具体内容，再让程序执行有限操作。

本课只写教学报告，不提交论文、不发送邮件，也不修改原始科研数据。完成后要能指向输出文件和批准记录，而不能把“程序生成了一份文本”当成内容已经经过科学审核。

### 改一改 · 修改草稿，观察旧批准为什么失效

- 先执行 python run.py day 17，将 outputs/day17.json 复制为自己的基线备份。

- 在 VS Code 打开 experiments.json，只修改 day17.draft_text 为 "Teaching report: this is a revised draft."，保持其他键不变并保存。

- 执行 python -m json.tool experiments.json 检查语法，再执行 python run.py day 17。

- 对比两份结果，重点观察status、digest、preview 和 path；解释改变原因后恢复原设置或明确记录保留值。

**观察什么：**先完成一次批准写入，再只修改 draft_text 并保留旧 approved_digest；程序应拒绝把旧批准用于新内容。

**机制解释：**审批必须绑定到当前具体内容，不能因为用户曾经批准过一次就持续执行变化后的动作。

## 常见问题

### 修改配置后结果没有变化

原因：改了其他天的字段，或编辑后尚未保存。

处理：核对 experiments.json 中的 day17，保存后重新运行；检查实际执行目录。

### 把受控失败误当成程序坏了

原因：本课实验主动制造了边界条件。

处理：先对照 expected 和状态字段，区分设计内拒绝与未处理异常；保留错误信息再修复。

## 自测与解析

### 1. 修改待写内容后，之前的 approved_digest 应如何处理？

- A. 永久有效

- B. 自动替换为新摘要

- C. 需要重新审阅并批准

- D. 忽略摘要继续执行

**答案：C。** 旧批准只对应旧内容，新内容需要新的审阅。

### 2. already_applied 主要说明什么？

- A. 科学结论已被验证

- B. 相同操作已执行，重复请求没有再次写入

- C. 所有用户都拥有写权限

- D. 报告内容永远不能改

**答案：B。** 这是执行层面的幂等状态，不代表科学正确性或普遍授权。

## 小词典

- **Digest**：由内容计算的摘要，可用于检验内容是否改变。

- **Idempotency**：重复执行同一操作时避免重复产生效果的性质。

- **Approval**：用户对明确对象、内容与动作作出的批准。
