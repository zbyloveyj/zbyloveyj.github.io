## 01 · 理解概念

### 评价首先要说明题目与标准

评价集是一组问题及其预先写明的期望。今天使用data/eval_dev.json公开教学开发集，其中可回答题具有应出现的证据ID，不可回答题没有支持证据。先读一条题目和标签，再看系统表现，避免事后根据输出修改正确答案。

这些案例数量很小、全部公开，适合发现接口与流程问题。它们不是隐藏测试，更不是对真实科研能力的独立验证。开发集上得分提高，说明在这套明确规则下变好；是否能推广到新问题，需要另做评价。

### 检索召回回答的是“找回来多少”

一条可回答题的证据召回等于“检索到的期望证据数量÷全部期望证据数量”。例如需要E03和E07，只找到E07，这条题的召回是1/2。当前程序对可回答题逐题计算，再求平均；无支持证据题的召回记为null，不把它塞进相同分母。

召回不惩罚所有无关材料。找回正确证据的同时夹入很多噪声，召回仍可能很高。因此要打开items检查具体结果，并考虑回答是否引用全部必要材料、是否引入不支持的主张。不要用一个数字替代全部质量判断。

### 可回答与不可回答分别检查

当前answerable_accuracy的通过条件是状态为answered，且引用集合包含该题全部期望证据ID。abstention_accuracy则统计本来没有支持证据的题，系统是否返回abstained。它们是教学程序的规则指标，不会自动判断自然语言中的每个科学结论。

这个区别能发现一种常见失败：系统给出了答案，引用也真实，却遗漏了题目必须同时考虑的另一条证据。另一种失败是任何问题都回答；如果没有单独设置不可回答题，漂亮的总体结果可能掩盖这种问题。

### 让检索与回答使用同一个实验条件

今天的top_k同时传给检索和回答路径，避免一边评价取1条、另一边回答偷偷取3条。先用1，再用3，其他条件保持不变。比较时记录配置、每个指标的分母，以及哪一题发生变化。

当前教学集D6要求同时覆盖E03和E07，top_k=1无法同时取回两条；top_k=3能够展示完整覆盖的区别。这个案例说明了指标如何定位缺口，不代表以后top_k越大越好：更多材料也会增加噪声和上下文成本。

## 02 · 一步一步做

命令在解压后的 practice 文件夹执行。Windows可使用 .\.venv\Scripts\python.exe；macOS/Linux可使用 .venv/bin/python 替代 python。

### 1. 运行公开开发集

**为什么做：**建立与后续修改可比较的基线。

保持day11.split为dev、top_k为3，运行本课。

```text
python run.py day 11
```

**预期结果：**得到evaluation中的retrieval_recall、answerable_accuracy、abstention_accuracy和items。

### 2. 直接比较两个检索数量

**为什么做：**确保参数真实传入评价程序。

依次运行下面两条命令，把两次终端结果复制到学习笔记；同名evaluation_dev.json会更新。

```text
python run.py evaluate --split dev --top-k 1
python run.py evaluate --split dev --top-k 3
```

**预期结果：**top_k=1时D6缺少部分期望证据；top_k=3时该教学案例覆盖完整。

### 3. 回到失败题核对分母

**为什么做：**从指标追到具体材料。

打开开发集与结果，找到D6的expected和retrieved，再人工算一次该题召回。

```text
python -m json.tool data/eval_dev.json
python -m json.tool outputs/evaluation_dev.json
```

**预期结果：**能够解释这条题的1/2与整体平均值为什么不同。

### 4. 写一段评价结论

**为什么做：**把观察与推广范围分开。

用三句话记录配置、发生变化的案例、仍未检验的能力；不要把公开小题集得分写成科学结论正确率。

**预期结果：**结论包含分母与适用范围，指出仍需人工核对语义支持。

### 改一改 · 让D6从部分证据变成完整证据

- 在experiments.json中只把day11.top_k改为1，运行python run.py day 11。

- 记录D6的expected、retrieved、recall和passed，再将top_k改回3运行。

- 对照其余题是否变化；解释为什么当前测试的改善不意味着所有问题都应增加检索数量。

**观察什么：**当前公开教学集中D6从部分覆盖变为完整覆盖；指标计算使用同一个top_k驱动检索与回答。

**机制解释：**逐题记录让数字变化具有可解释的原因；结果仅反映本套公开开发题的规则检查。

## 常见问题

### 只看到最终一次评价结果

原因：两次命令写入同名输出文件。

处理：运行下一次前复制终端结果到笔记，或给自己的记录注明配置；不要把两次混成一份。

### 达到满分就认为可以交付真实研究

原因：当前题目很少且已公开，指标按证据ID和状态计算。

处理：追加人工检查与新问题，并把公开开发集范围写入报告；不要修改标签迎合输出。

## 自测与解析

### 1. 一题需要E03和E07，检索只找到E07，该题召回是多少？

- A. 0

- B. 1/2

- C. 1

- D. 无法计算

**答案：B。** 已找到1条期望证据，共需2条，因此召回是1/2；无关材料多少不改变这个分母。

### 2. 公开开发集上的高分最直接说明什么？

- A. 所有科研问题都能正确回答

- B. 模型拥有真实科研能力

- C. 当前实现通过了这套已知题目的规定检查

- D. 无需再检查拒答

**答案：C。** 它证明的是明确题集与指标下的表现，不能替代未知问题测试或科学语义验证。

## 小词典

- **召回**：检索到的期望证据占全部期望证据的比例。

- **开发集**：用于观察和改进系统的已知案例集合。

- **拒答评价**：检查没有支持材料时是否明确停止作答。
